## а) Рабочие места Linux (330 шт) — РЕД ОС + FOG + Ansible-pull

### Шаг 1. Эталонный образ РЕД ОС 8

Ставим на эталонный mini-PC (ThinkCentre M75q — основная модель, docs/05) РЕД ОС 8 с нуля и наполняем:

| Компонент | Что и зачем |
|---|---|
| Р7-Офис | `.deb` из локального зеркала (лицензия ~3 тыс./польз./год) |
| Яндекс.Браузер | корпоративная сборка, политики: стартовая = CRM, запрет смены поисковика |
| GLPI-агент | инвентаризация + helpdesk (`glpi-agent`, server → http://10.10.30.12) |
| zabbix-agent2 | мониторинг АРМ (host → 10.10.30.11) |
| Софтфон | для КЦ-роли (MicroSIP/twinkle — ставится post-install, не в образ) |
| Политики | отключён USB-storage для не-привилегированных, парольная политика, автоэкран-блок 10 мин, обои/брендинг, NTP → ntp1.vniiftri.ru |
| Учётка | локальный админ `itadmin` (пароль из OpenBao), пользователи — позже через ALD Pro |

Очистка перед захватом: `journalctl --vacuum-time=1d`, очистить `/tmp`, историю, `apt clean`, удалить SSH host keys (регенерируются при первой загрузке через cloud-init/скрипт).

### Шаг 2. Захват образа в FOG

1. FOG Server уже развёрнут ролью `iac/ansible/roles/fog` (ВМ fog-01, 10.10.30.20).
2. На UserGate/ядре DHCP: `next-server 10.10.30.20`, `filename "ipxe.efi"` (UEFI) / `"undionly.kpxe"` (BIOS).
3. В FOG UI: зарегистрировать эталонный хост (PXE → Quick Registration), создать образ `redos8-thinkcentre-m75q` (тип: Single Disk — Resizable, Partclone).
4. Хосту назначить образ → Tasks → **Capture**. Машина загружается по PXE, заливает образ (~20–40 мин на 512 ГБ SSD, реально передаётся только занятое).

### Шаг 3. Развёртывание — в т.ч. multicast на этаж

- **Точечно (1–10 мест):** PXE → FOG Boot Menu → Deploy, либо из UI Tasks. ~10–15 мин на место, параллельно 5–8 шт без просадки сети.
- **Multicast на этаж (20–60 мест):** в FOG UI создать Multicast-задачу на образ, включить все машины этажа в группу, загрузить их по PXE — они ждут старта сессии, FOGMulticastManager вещает образ одним потоком. **Проверить:** IGMP snooping на этажных свитчах включён, иначе multicast утонет в широковещание и положит VLAN.
- Hostname и имя в GLPI назначаются FOG Client (или post-install скриптом по таблице MAC→имя).

### Шаг 4. Post-install: ansible-pull из монорепы

Каждая машина после первой загрузки (systemd-oneshot) выполняет:

```bash
ansible-pull -U https://git.corp.crmfactory.local/iac/ansible.git \
  -e workstation_role=office \   # или callcenter / developer
  playbooks/site.yml
```

Роль `linux_desktop` доставляет роль-специфичный софт (софтфон для КЦ, IDE для разработчиков), конфиг GLPI-агента, киоск. Далее pull повторяется по cron раз в час — конфигурация самовосстанавливается.

### Шаг 5. Киоск колл-центра (60 мест)

- `workstation_role=callcenter` → роль `linux_desktop` кладёт `/etc/xdg/autostart/kiosk.desktop`: autologin под `operator`, браузер в kiosk-режиме на URL CRM + софтфон на фоне.
- Блокировки: запрет TTY-свитча, отключён терминал из меню, автологаут при простое смены нет (24/7).
- Восстановление образа киоска через FOG — **10 минут**, это главный механизм «ремонта» КЦ.

### Тайминги (реалистично, один админ)

| Этап | Темп |
|---|---|
| Сборка эталонного образа (первый раз) | 2–3 дня |
| Распаковка + стойка + PXE multicast этажа (~40 мест) | 1 день на этаж |
| Точечная заливка | 8–12 мест/день (unicast, параллельно) |
| **Итого 330 мест** | **~3–4 недели** с обходом пользователей и переносом профилей |
| Пересборка эталона (ежеквартально) | 0,5–1 день |

## б) Рабочие места Windows (70 шт) — MDT + WDS + KMS + WSUS

### Шаг 1. Инфраструктура на ВМ

Одна ВМ Windows Server (или Win11 + ADK): роли **WDS** (PXE-загрузка boot.wim) + **MDT 8456** (сборка образов). Deployment Share на отдельном диске 300 ГБ. DHCP-опции 66/67 — на UserGate (66 = IP WDS, 67 = `boot\x64\wdsnbp.com`).

### Шаг 2. Эталонный образ Windows 11

- Исходник: чистый ISO Windows 11 Pro 23H2+ (бессрочные лицензии/«серые» ключи — по решению из docs/05).
- В MDT: Task Sequence «Ref-Win11» — установка ОС → **обезличивание** (sysprep /generalize /oobe, без привязки к учёткам) → захват в install.wim.
- **Драйвер-паки:** в MDT Out-of-Box Drivers — по папке на модель: `ThinkCentre M75q`, `Huawei MateBook D16`, `ThinkPad E14` (2–3 модели, docs/05). MDT сам подставит по WMI-запросу модели при развёртывании.
- **Софт в Task Sequence (Applications):** КриптоПро CSP 5.0, 1С-клиент (толстый+тонкий, конфиг бухгалтерии), банк-клиенты (СберБизнес + конкретный банк из риска docs/05), Р7-Офис, GLPI-агент (FusionInventory для Win), zabbix-agent2, ВКС-клиент.
- Всё тяжёлое ПО ставить тихими ключами (`/S`, `/quiet`, msiexec /qn) — логи в `C:\Windows\Temp\deploy`.

### Шаг 3. KMS-активация

- ВМ с ролью **KMS (Volume Activation Services)**; публикуется в DNS (`_vlmcs._tcp` SRV).
- Клиенты — GVLK-ключи Windows 11 Pro в Task Sequence (`slmgr /ipk W269N-...`); активация автоматическая при ≥25 клиентах (KMS-порог).
- Если легальных KMS-ключей нет — MAK-активация поштучно через Task Sequence (учёт ключей в Vaultwarden).

### Шаг 4. Локальный WSUS

- ВМ WSUS (роль Windows Server), продукты: Windows 11 + Defender; классы: Critical + Security + Updates. Автоодобрение критических.
- Клиенты нацелены на WSUS через локальную политику (до ввода ALD Pro) / GPO ALD Pro позже: `Specify intranet Microsoft update service location → http://wsus-01:8530`.
- Кольца: пилотная группа (5 машин бухгалтерии) → неделя → весь парк. WSUS deprecated, но обновления Win11 публикуются — живём на нём до ALD Pro Policy Manager.

### Тайминги

Сборка инфраструктуры MDT+WDS+WSUS — 3–4 дня; эталонный образ — 2 дня; развёртывание — 15–25 мест/день (литерально: PXE → выбор Task Sequence → 30–40 мин на машину, 4–6 параллельно). **70 мест ≈ 1,5 недели.**

## в) Телефония MikoPBX — по шагам

### Шаг 1. Установка (ВМ ×2)

1. Скачать ISO MikoPBX (Generic x64) с mikopbx.ru.
2. ВМ `pbx-01` на ноде PVE-1: 2 vCPU / 4 ГБ / 50 ГБ (записи разговоров — отдельный диск 200 ГБ или NFS). ВМ `pbx-02` (горячий резерв) на ноде PVE-2 — клон с теми же ресурсами, IP из VLAN VOICE.
3. Консольное меню MikoPBX → задать статический IP, пароль root, включить веб-интерфейс https://pbx-01.
4. Сразу: **Настройки → Резервное копирование** → ежедневный бэкап конфига на файловое хранилище; на pbx-02 настроить восстановление из последнего бэкапа (репликация конфига — docs/06).

### Шаг 2. Два SIP-транка с failover

1. **Провайдеры → Добавить:** транк `MTT-main`: host из ЛК МТТ, логин/пароль, регистрация — да.
2. Транк `RT-backup` (Ростелеком): аналогично по своим реквизитам.
3. **Маршрутизация → Исходящая:** правило `8XXXXXXXXXX` → сначала MTT-main, вторым провайдером в том же правиле — RT-backup (MikoPBX сам перебирает при недоступности/занятости). Проверка failover: выключить сетевой интерфейс транка МТТ → звонок должен уйти через РТ без вмешательства.
4. Периодический qualify (OPTIONS) включён на обоих транках — основа для триггера «SIP-транк даун» в Zabbix.

### Шаг 3. План нумерации

| Диапазон | Назначение |
|---|---|
| 1XX (100–199) | офис: руководители 10X, продажи 11X–13X, бухгалтерия 14X, разработка 15X–16X |
| 2XX (200–269) | колл-центр: операторы 200–249, супервизоры 250–259 |
| 3XX | конференц-комнаты, переговорки |
| 800/801 | очередь КЦ, очередь техподдержки (сервисные) |

Сотрудники → внутренний номер, DID (прямой городской из пула МТТ) при необходимости, voicemail на почту VK WorkSpace.

### Шаг 4. Очередь колл-центра

**Приложения → Очереди → 800 «КЦ-основная»:**

- **Стратегия: `rrmemory`** (round-robin с памятью — равномерная нагрузка, не «спамим одного»).
- **Запись разговоров: все** (режим «запись включена», хранение 90 дней, дальше — в архив/S3; записи — ссылкой в CRM).
- **Время ожидания:** max 300 сек, объявление позиции в очереди — да, periodic-announce каждые 60 сек («все операторы заняты…»).
- Timeout агента 20 сек, wrap-up 15 сек, музыка ожидания — корпоративная.
- Переполнение (>10 в очереди или >300 сек) → IVR «перезвоните позже» + лист ожидания супервизору (модуль «Контроль качества» из маркетплейса).

### Шаг 5. IVR приветствие

**Система → Медиафайлы:** загрузить записанные промпты (приветствие, меню, «все заняты»). **Маршрутизация → IVR-меню «Главное»:**

```
Приветствие (записано диктором или TTS из маркетплейса):
«Здравствуйте, вы позвонили в <Компания>. Техподдержка — 1,
отдел продаж — 2, бухгалтерия — 3. Ожидайте ответа оператора — 0.»
  1 → очередь 800 (КЦ)
  2 → очередь 801 (продажи)
  3 → внутренний 140 (бухгалтерия)
  0/timeout → очередь 800
Нерабочее время (23:00–07:00, только для офисных направлений):
  → голосовая почта на support@; КЦ работает 24/7 — своя ветка без расписания
```

### Шаг 6. Маршрутизация входящих 8-800

**Маршрутизация → Входящие:** правило по DID `8800XXXXXXX` (транк МТТ) → IVR «Главное» → (0/таймаут) → очередь 800. Прямые городские DID сотрудников маршрутизируются напрямую на внутренние 1XX (правило DID→extension).

### Шаг 7. Интеграция с CRM через AMI

1. **Система → Asterisk Managers:** пользователь `crm-ami`, пароль из OpenBao, permit = сеть CRM-серверов.
2. CRM подключается к AMI (порт 5038, лучше через TLS-туннель/SSH). События `Newchannel`/`Dial`/`Hangup` → карточка клиента по номеру, запись разговора — ссылкой из MikoPBX API.
3. **Click-to-call — originate:**

```
Action: Originate
Channel: PJSIP/201            # внутренний номер оператора (КЦ 2XX)
Context: from-internal
Exten: 84951234567            # номер клиента
Priority: 1
CallerID: "CRM <201>"
Timeout: 30000
Async: true
```

Сначала звонит оператору (поднял трубку), затем набирается клиент. Аналог через REST MikoPBX: `POST /pbxcore/api/call/v1/call/{number}` — что удобнее разработчикам CRM.

### Шаг 8. Failover на облачный профиль МТТ («здание сгорело»)

1. В ЛК МТТ: на 8-800 включить **условную переадресацию по недоступности** на облачный профиль/номера (мобильные супервизоров или облачная АТС МТТ с тем же IVR — настраивается заранее, не в момент аварии).
2. Сценарий: при потере канала/здания МТТ сам перебрасывает 8-800 в облако → операторы работают с софтфонов на ноутбуках (домашний интернет). Тест сценария — раз в квартал.
3. pbx-01 недоступна → переключение на pbx-02 (другая нода кластера): телефоны перерегистрируются на резервный IP (DNS SRV/NAPTR или смена A-записи pbx внутреннего DNS, TTL 60 сек). RTO ≤ 15 мин.

## г) Мониторинг: Zabbix + Telegram + Grafana

### Хосты в Zabbix (шаблоны)

| Группа хостов | Что | Как |
|---|---|---|
| PVE-ноды | 2–3 ноды кластера | zabbix-agent2 + шаблон «Proxmox VE by HTTP» (API-токен PVE, read-only) |
| Свитчи | ядро + этажные | SNMPv3, шаблон вендора (Eltex/MikroTik — interfaces, CPU, PSU, PoE) |
| ИБП | серверная + этажные | SNMP (карта/network card ИБП), шаблон APC/Eaton по факту |
| NetPing | климат серверной | SNMP: t°, влажность, датчик дыма/протечки, состояние ДГУ (сухие контакты) |
| MikoPBX | pbx-01/02 | zabbix-agent2 + UserParameter: `asterisk -rx "core show channels count"`, статус транков через AMI-скрипт |
| ВМ сервисов | fog-01, zabbix, GLPI, MDT/WSUS, GitLab, Nextcloud, PBS, AD DC (ALD Pro) | zabbix-agent2, стандартные шаблоны OS Linux/Windows |
| АРМ (по желанию) | 400 мест | agent2, активные проверки; минимум — КЦ (60 шт) |

### Триггеры уровня «звонить админу» (severity High/Disaster → Telegram)

| Триггер | Выражение (суть) | Severity |
|---|---|---|
| Нода PVE даун | agent unreachable 3 мин + нет ICMP | **Disaster** |
| Ceph HEALTH_WARN/ERR | item `ceph.status` ≠ HEALTH_OK 5 мин | **High** (ERR → Disaster) |
| ИБП на батарее | `upsBasicOutputStatus = onBattery` | **High** (осталось <20% → Disaster) |
| SIP-транк даун | AMI/registry: транк unreachable или qualify fail 2 мин (отдельно МТТ, отдельно РТ) | **High** (оба → Disaster: телефония лежит) |
| Datastore < 15% свободно | `vfs.fs.size[/,pfree] < 15` на PVE/PBS, и по пулам Ceph | **High** |
| ДГУ запущен / NetPing: t° > 28 °C, дым, протечка | SNMP | **High/Disaster** |

Остальное (диск ВМ, CPU, сертификаты, бэкап PBS не прошёл) — Warning/Average в тот же Telegram, но с тегом `#info`.

### Алерты в Telegram

- Медиатип: скрипт `iac/zabbix/telegram-webhook.sh` → AlertScriptsPath (chat_id/токен из макросов `{$TG_CHAT_ID}`/`{$TG_BOT_TOKEN}` — последний типа Secret, либо env zabbix-server; не коммитить, group_vars тянет из OpenBao/env).
- Получатель: группа «Дежурные ИТ»; действие (Trigger action): conditions — severity ≥ High; recovery messages включены (✅ «Resolved»).
- Эскалация: если PROBLEM не подтверждён (ack) за 15 мин — повторная отправка + отдельное сообщение руководителю ИТ.

### Дашборд Grafana для руководства

Источник: Zabbix plugin для Grafana (прямой SQL запрещён). Один дашборд «Состояние ИТ» на ТВ/планшет гендира:

- **Uptime КЦ (SLA):** доступность очереди 800 за месяц, % (цель 99,5%).
- **Звонки в очереди:** график текущих ожидающих + пропущенные за день (item MikoPBX), среднее время ожидания.
- **Состояние ДГУ/электропитания:** стат-панель «Сеть / ИБП / ДГУ» (зелёный/красный), время автономии ИБП.
- Инфра: живость нод/ВМ (donut), свободное место datastore, количество открытых PROBLEM.
